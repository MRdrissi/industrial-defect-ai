# US-05-01 — Pipeline commun d'évaluation scientifique

**Epic : EPIC-05 · Jira : IDL-54 · Branche : `epic/05-evaluation-benchmark`**

Le pipeline calcule et exporte les mêmes métriques à partir des prédictions CAE et PatchCore.
Il ne charge pas de checkpoint, n'entraîne aucun modèle et ne choisit aucun seuil.
La validation livrée porte sur des données synthétiques, pas sur les performances de MVTec AD.

## Architecture et contrats

| Module | API publique et responsabilité |
|---|---|
| [metrics.py](../../src/evaluation/metrics.py) | `compute_image_metrics(labels, scores, threshold=None)` ; `compute_pixel_auroc(masks, anomaly_maps)` |
| [masks.py](../../src/evaluation/masks.py) | `prepare_ground_truth_mask(mask, label, target_size)`, `resize_binary_masks`, `resize_anomaly_maps`, `align_pixel_inputs(masks, anomaly_maps, target_size=None)` |
| [latency.py](../../src/evaluation/latency.py) | `measure_inference(predict, *, synchronize=None)` ; `benchmark_latency(predict, *, warmup=3, repetitions=10, synchronize=None)` |
| [exporters.py](../../src/evaluation/exporters.py) | `EvaluationRecord`, `export_evaluation(output_dir, records, metrics, run_config)`, `file_sha256(path)` |
| [benchmark.py](../../src/evaluation/benchmark.py) | `evaluate_predictions(records, *, threshold=None, output_dir=None, run_config=None)` : validation, calcul commun, export optionnel |

Un `EvaluationRecord` contient :

| Champ | Contrat |
|---|---|
| `image_path` | Chemin relatif POSIX canonique, unique dans le run, sans traversée, lecteur Windows ou caractère de contrôle |
| `label` | Entier : **0 = normale, 1 = anomalie** |
| `score` | Scalaire réel fini ; une valeur élevée indique davantage d'anomalie ; ce n'est pas une probabilité |
| `mask` | Tableau NumPy [H,W], binaire 0/1 ; nul pour une normale, au moins un pixel positif pour une anomalie |
| `anomaly_map` | Tableau réel fini [H,W], mêmes dimensions que le masque ; aucune normalisation par image |
| `latency_ms` | Durée finie et non négative, mesurée par l'appelant dans le périmètre déclaré |

Détacher les tenseurs et les transférer sur CPU avant conversion NumPy.
Les cartes sont conservées en **float64** pendant l'évaluation et dans les NPZ.
Cela évite de transformer deux scores float64 distincts en ex æquo float32, ce qui modifierait l'AUROC.
Cette conversion ne récupère pas une précision déjà perdue à l'inférence.

Le benchmark exige une résolution commune et refuse les chemins dupliqués.
Il retourne `n_images` et les rubriques `image` (métriques et TP/TN/FP/FN), `pixel` et `latency`.
Sans export, aucune métadonnée de run n'est nécessaire.
Pour exporter, fournir ensemble `output_dir` et `run_config`.
Le seuil utilisé est enregistré automatiquement ; toute contradiction avec la configuration est refusée.

## Définition des métriques

Pour un score continu \(s\) et un seuil fixé \(t\), la décision est
\(\hat y = \mathbf{1}[s > t]\) : **un score égal au seuil reste normal**.

- **Image-AUROC** : \(P(s_+ > s_-) + \frac12 P(s_+ = s_-)\), sur les scores continus des images.
- **Precision** : \(TP/(TP+FP)\).
- **Recall** : \(TP/(TP+FN)\).
- **F1** : \(2TP/(2TP+FP+FN)\).
- **Pixel-AUROC** : même définition de l'AUROC, après concaténation des pixels de toutes les cartes et de tous les masques. Les normales et leurs pixels négatifs sont inclus ; ce n'est pas une moyenne des AUROC par image.

Les calculs utilisent scikit-learn, avec `zero_division=0`.
Une AUROC exige les deux classes ; sinon elle vaut `None` en Python et `null` en JSON.
Sans seuil, Precision/Recall/F1 et les effectifs de confusion valent également `None`.
Avec seuil, un dénominateur nul donne **0 par convention**, même si la quantité est mathématiquement indéfinie.
Les effectifs de classe et de confusion permettent d'interpréter ces zéros.
Les entrées vides, dimensions incompatibles, NaN, infinis, scores complexes et masques non binaires sont refusés.

## Masques et résolution de référence

La [configuration](../../experiments/configs/evaluation_protocol.json) fixe **256 × 256** pour les six instances.
Les utilitaires acceptent aussi d'autres tailles pour les tests ; ils ne chargent pas automatiquement ce JSON.
L'appelant doit passer explicitement `target_size=(256, 256)` à l'alignement et renseigner
`target_size_hw` dans le run. L'export vérifie cette taille contre les données.
Sans taille explicite, `align_pixel_inputs` conserve la résolution du masque : ce défaut générique ne remplace pas le protocole.

- Masques : nearest-neighbor Pillow, sortie uint8 0/1. Convertir explicitement les masques bruts 0/255 en booléens dans l'adaptateur.
- Cartes : interpolation bilinéaire CPU avec `torch.nn.functional.interpolate`, float64,
  `align_corners=False`, `antialias=True`. Ces paramètres sont enregistrés dans le protocole.
  Sans changement de taille, les valeurs sont conservées.
- Une normale sans masque reçoit un masque nul. Une anomalie sans masque ou avec masque nul est refusée.
- Si un masque positif devient entièrement nul au redimensionnement, une erreur donne les indices concernés.
  Ne pas supprimer l'image, inventer des pixels positifs ou adapter la résolution séparément selon le modèle.

Le nearest-neighbor peut encore réduire la surface d'un défaut ou supprimer un composant parmi plusieurs.
Le contrôle détecte la disparition **totale**, pas la conservation de chaque composant.
L'appliquer avant le premier redimensionnement : une disparition en amont n'est pas reconstructible.
Toute révision de résolution doit rester commune aux instances et ne pas être choisie pour améliorer les scores du Test.

## Exports et traçabilité

Utiliser `evaluate_predictions` pour que les métriques exportées proviennent des records fournis.
L'exporteur bas niveau sérialise des métriques données par l'appelant sans les recalculer.

| Fichier | Contenu |
|---|---|
| `predictions.csv` | index, image_path, label, score, latency_ms, artifact_file, artifact_sha256 |
| `artifacts/00000.npz`, etc. | masque uint8 et carte float64 ; lecture avec `np.load(..., allow_pickle=False)` |
| `metrics.json` | version du schéma, provenance, métriques, nombre d'images et résumé de latence |
| `manifest.json` | SHA-256 des NPZ, du CSV et du JSON des métriques ; chemins permettant de les revérifier |

Le JSON est UTF-8 sans BOM et refuse les valeurs non finies.
Les champs obligatoires sont partagés avec le protocole :
`run_id, model_family, category, split, git_commit, checkpoint_sha256, dataset_manifest_sha256, device, hardware, python_version, torch_version, threshold, latency_scope, target_size_hw`.
Le commit comporte 40 chiffres hexadécimaux et les SHA-256, 64.
La validation du format ne prouve pas l'authenticité : calculer les empreintes sur les fichiers réellement utilisés.
Ajouter les versions NumPy/scikit-learn/Pillow, le prétraitement, la définition du score et les références de calibration au run.

L'export refuse toute destination existante, prépare les fichiers dans un dossier temporaire voisin,
puis publie ce dossier par renommage. Un verrou exclusif empêche deux exporteurs coopérants de publier le même run.
Les tests vérifient le nettoyage après erreur et la préservation d'une destination apparue pendant l'écriture.
Un arrêt brutal peut laisser un verrou bloquant : vérifier qu'aucun processus n'écrit avant toute intervention.
Ce mécanisme n'est ni une transaction distribuée ni une garantie de durabilité après panne électrique.
Les SHA-256 détectent une altération par rapport au manifeste ; ils ne signent pas indépendamment le manifeste.

`split` (`val` ou `test`) et les empreintes sont des déclarations de provenance.
Le pipeline ne relit pas les manifestes pour prouver l'appartenance des chemins.
Le futur orchestrateur devra la vérifier : un chemin physique `train/good` peut appartenir au split logique Validation.
Voir [US-02-03](../epic-02/us-02-03.md) et [US-02-04](../epic-02/us-02-04.md).

## Latence

Le protocole prévoit un batch de **1**, **3 warm-ups exclus**, puis une mesure par image.
`measure_inference` retourne la prédiction et la durée en millisecondes, via `time.perf_counter`.
`benchmark_latency` répète une fonction (10 répétitions par défaut) et retourne les durées brutes,
moyenne, médiane, p95 linéaire, minimum et maximum. Le benchmark agrège les durées des records.

Le périmètre `model_inference_only` exclut disque, prétraitement et transfert CPU/GPU.
Préparer les entrées avant la fonction chronométrée et documenter son contenu pour CAE et PatchCore.
Appeler le modèle en `eval()` sous `torch.inference_mode()` ; les utilitaires ne changent pas son état.
Pour CUDA, transmettre `synchronize=lambda: torch.cuda.synchronize(device)` :
synchronisation avant le départ du chronomètre et après la prédiction, avant son arrêt.
Sans callback, une mesure CUDA peut ne mesurer que le lancement asynchrone ; le device n'est pas détecté automatiquement.

Les tests CPU vérifient l'ordre des événements avec un callback simulé.
Ils ne constituent pas un benchmark GPU ni une validation du matériel CUDA.
Documenter matériel, versions, device, batch, warm-ups et périmètre identique entre instances.

## Utilisation minimale

Depuis la racine, cet exemple synthétique vérifie le contrat sans écrire de résultat expérimental :

```python
import numpy as np
from src.evaluation.exporters import EvaluationRecord
from src.evaluation.benchmark import evaluate_predictions

records = [
    EvaluationRecord("synthetic/good.png", 0, 0.1,
                     np.zeros((2, 2), dtype=np.uint8),
                     np.full((2, 2), 0.1), 1.0),
    EvaluationRecord("synthetic/defect.png", 1, 0.9,
                     np.array([[0, 1], [0, 0]], dtype=np.uint8),
                     np.array([[0.1, 0.9], [0.1, 0.1]]), 1.0),
]
report = evaluate_predictions(records, threshold=0.5)
# Pour exporter des prédictions réelles :
# evaluate_predictions(records, threshold=frozen_threshold,
#                      output_dir=unique_run_directory, run_config=provenance)
```

Les durées ci-dessus sont fictives. [test_benchmark.py](../../tests/evaluation/test_benchmark.py)
montre l'export complet avec une provenance explicitement synthétique.

## Limites et étapes suivantes

Le JSON fixe à l'avance un quantile **0,95**, interpolation linéaire, sur les normales Validation,
séparément pour les six instances. Ce paramétrage n'exécute aucune calibration.
[US-05-02](us-05-02.md) fige désormais le score CAE dans le protocole 1.1.0 et vérifie les chemins. Il reste à
produire/versionner les six seuils et leur provenance, puis prouver l'exclusion du Test.
Aucune normalisation des scores ni sélection de seuil à partir du Test n'est autorisée.

**US-05-03** réalisera le benchmark réel, les macro-moyennes non pondérées par catégorie
et le décompte des métriques indéfinies. Ces agrégations inter-runs figurent dans le protocole mais
ne sont pas encore implémentées dans US-05-01. Résolution et seuils seront fixés avant le test final.

Le Pixel-AUROC concatène les pixels en mémoire ; son coût augmente avec le nombre d'images,
la résolution et les copies float64. Le fond normal peut dominer cette métrique, qui ne mesure pas la qualité des frontières.
Aucun AUROC/F1 réel, calibrage, benchmark GPU, intervalle de confiance ou performance de localisation n'est revendiqué ici.
