## Protocole et correction

Le pipeline [US-02-04](../epic-02/us-02-04.md) charge le
[manifeste Hazelnut](../data/us-02-03/hazelnut_manifest.csv) :
**313 normales Train, 78 normales Validation, 110 images Test**, avec des chemins uniques et disjoints.
Les 313 chemins réellement traités sont archivés dans le
[rapport coreset](../data/us-04-04/EXP-002/coreset_report.json) et correspondent exactement au Train.
Aucune normale de Validation ni image du Test officiel n'entre dans la banque.

Backbone `wide_resnet50_2` pré-entraîné et gelé ; couches `layer2` et `layer3`.
Le profil `patchcore` de `MVTecTransform` applique le RGB, le resize bilinéaire 256 × 256,
puis la normalisation ImageNet. Batch 2, workers 0, seed 42, aucune optimisation par epochs.

Les cellules GPU 7 et 9 utilisent la même chaîne :
`feature_extractor → feature_pooler sur chaque couche → generate_embedding → reshape_embedding`.
Le pooling local est celui du modèle Anomalib : moyenne 3 × 3, stride 1, padding 1.
L'alignement multirésolution et la concaténation produisent 1 024 patches de dimension 1 536 par image.

La cellule GPU 8 compare l'extraction manuelle au `forward()` officiel Anomalib 2.7.0
sur **deux normales** : deux matrices [2048,1536], **écart maximal 0,0**, PASS.
Le backbone reste en mode évaluation pendant ce contrôle ; le magasin temporaire
`embedding_store` est vidé dans un `finally`.
Cette parité observée porte sur ce batch, pas sur une comparaison exhaustive de chaque image.

## Construction de la banque

La collecte complète (cellule GPU 9) réinitialise le DataLoader, préalloue une matrice float32
CPU et copie chaque lot dans sa tranche. Elle utilise l'extraction directe avec pooling,
sans appeler le forward d'entraînement qui accumulerait les embeddings sur GPU.
Le magasin interne reste vide ; les tenseurs temporaires GPU sont libérés après chaque lot.

La cellule 11 sélectionne le coreset à partir de cette matrice corrigée :
`KCenterGreedy`, ratio 0,01, projection epsilon 0,9.
Python, NumPy, Torch et CUDA sont seedés à 42 ; la projection reçoit explicitement
`random_state=42`. Les 3 205 indices sont uniques et bornés ; ils sélectionnent les vecteurs
originaux corrigés de dimension 1 536. La banque obtenue est attachée au modèle.

## Sauvegarde, inférence et restauration

La cellule GPU 12 sauvegarde `state_dict` (backbone et banque) et `config`.
Les versions Torch/Torchvision sont converties en chaînes : le chargement
`weights_only=True` réussit sans autorisation supplémentaire de `TorchVersion`.

L'inférence GPU (cellule 13) utilise **le modèle en mémoire qui vient d'être sauvegardé**,
avec la même banque ; elle ne recharge pas un nouveau modèle GPU depuis le fichier.
Le checkpoint est relu pour vérifier son chargement sûr et son SHA est contrôlé avant le rapport.

Le notebook CPU localise exclusivement EXP-002, contrôle les empreintes, restaure un modèle
`pre_trained=False` avec `strict=True`, sans clés manquantes/inattendues et sans nouveau coreset.
Il contrôle le hash du tenseur banque, le commit du pipeline et le manifeste.
Contrairement à l'export EXP-001, les cellules CPU de restauration contiennent ici leurs sorties.

Le [rapport CPU](../data/us-04-04/EXP-002/restore_report.json) et les sorties indiquent PASS.
Tolérances respectées : score ≤ 0,001 ; carte max ≤ 0,001 ; erreur max / étendue ≤ 0,0001.
Ce résultat établit une proximité numérique CPU/GPU, pas une identité bit à bit.

**Compatibilité US-04-05 :** le chargeur `load_patchcore` actuellement intégré attend
`model_state_dict`, `backbone`, `layers`, `num_neighbors` à la racine.
Le checkpoint Hazelnut utilise `state_dict` et `config` : il n'est pas directement accepté
par ce chargeur. La restauration dédiée EXP-002 est validée ; l'harmonisation de schéma
reste un travail à coordonner avec le responsable US-04-05. Aucun de ses fichiers n'est modifié.

## Reproduction et contrôles

1. Importer le notebook GPU EXP-002 dans une session T4 avec Internet et MVTec AD v2.
2. Vérifier les versions, le commit et le manifeste ; exécuter dans l'ordre, notamment la parité
   avant la collecte complète. Les dépendances transitives ne sont pas toutes verrouillées.
3. Sauvegarder une version avec Outputs ; conserver ses références et hashes sans écraser EXP-001.
4. Attacher ces Outputs et le dataset à une nouvelle session CPU, activer Internet pour les dépendances
   et le clonage, puis exécuter le notebook CPU EXP-002.
5. Vérifier l'identité EXP-002, les empreintes, le chargement strict et les trois tolérances.

La version exacte du dataset n’est pas inscrite dans ces exports ; v2 est la référence de reproduction du projet.

Les chemins `/kaggle/input/datasets/ipythonx/mvtec-ad` et `/kaggle/working` sont propres à Kaggle.
Les métadonnées Quick Save indiquent aucun accélérateur/input et Internet désactivé :
elles ne remplacent pas la configuration explicite des sessions.

Depuis la racine du dépôt :

```text
python -m pytest tests/data tests/models tests/inference tests/experiments -q
```

Les nouveaux tests vérifient les preuves, les chemins réellement traités, les rapports et les liens.
Ils exécutent sur CPU les affectations d'extraction du notebook avec de petites features synthétiques :
le pooling doit être consommé avant la concaténation ; une mutation qui l'omet doit changer le résultat.
Le contrôle de parité exporté est testé avec et sans écart, ainsi que son nettoyage du magasin.

Ces tests synthétiques utilisent un double de modèle et des opérations Torch de référence ;
ils ne prétendent pas réexécuter Anomalib ou son backbone. La parité réelle Anomalib 2.7.0
est celle du batch Kaggle conservé. Aucun dataset complet, GPU ou gros checkpoint n'est nécessaire.
